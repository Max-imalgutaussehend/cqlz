Benchmarks

Real measurements, including the ones that do not flatter us. Every number is reproducible with the commands at the bottom.

Machine: Apple M3, 8 cores, 16 GB, macOS 27, Rust 1.99 release builds, Criterion (median of 100 samples unless noted), ScyllaDB in Docker on the same machine. Treat absolute numbers as indicative; ratios matter more.

cqlc: front-end speed

Input: the 36 queries and schema of cqlc's shop example (about 5 KB). Comparison: sqlparser, the most widely used Rust SQL parser. It parses SQL, not CQL, so it only accepts 22 of the 36 statements; the table uses those 22 for the parse-to-parse row.

BenchmarkTimeThroughput
cqlc lexer, all queries13.9 µs298 MiB/s
cqlc parser, all queries52 µs79 MiB/s
cqlc full analysis: lex, parse, resolve schema, type-check 36 queries103 µs40 MiB/s
sqlparser parse, 22 accepted statements126 µs15.7 MiB/s
cqlc parse, the same 22 statements33 µs59.7 MiB/s

Reading: on identical statements cqlc's parser is about 3.8× faster than sqlparser's, and cqlc's complete analysis, which also checks every query against the schema, finishes in less time than sqlparser needs for parsing alone. Caveat: sqlparser is a general multi-dialect parser, so this shows cqlc is lean for CQL, not that sqlparser is slow.

cqlx: abstraction cost

In-process: building a statement (no network)

BenchmarkTime
cqlx type-state SELECT (2 partition keys, 1 range, limit; validated)320 ns
hand-written format! + boxed values (no validation)68 ns
cqlx insert_values() (4 columns)46 ns

The builder costs about 250 ns more than concatenating strings by hand. That buys compile-time partition-key enforcement and clustering validation. The type-state itself is free: the type parameters are zero-sized.

Against a real ScyllaDB (Docker): cqlx vs raw driver vs charybdis

Operationcqlxraw scylla drivercharybdis
select one partition (10 rows)142.7 µs148.0 µs147.1 µs
insert one row140.7 µs139.6 µs141.8 µs

All three use prepared statements on the same table and are indistinguishable within noise (±3%): a database round trip costs about 140 µs, so a 0.3 µs builder is invisible. "Zero overhead" holds in the sense that matters on the wire. charybdis is the closest existing Rust ORM for ScyllaDB; this is a single-node loopback test, not a cluster benchmark.

cql-ai: cost and sequence length

Benchmark (36 statements)Time
cql-ai tokenization (cqlc lexer + schema roles)43 µs
cql-ai Transformer forward, one batch of 36 (CPU, pure Rust)41 ms
cql-ai Transformer forward, single statement1.12 ms
cqlc deterministic analysis of the same 36 statements0.10 ms
cql-ai check end to end, wall clock incl. process start and loading weights≈ 52 ms
The honest comparison: the neural model is about 400× slower than cqlc's own analyzer on the statements both can handle. It still comfortably meets a CI budget (about 52 ms wall for a whole file, against a 500 ms target), but speed is not its selling point. Its niche is tolerating partial or non-compiling queries and reporting probabilities; use cqlc check when you have a complete schema and want certainty.

Sequence length

Representation (per statement, average)Length
UTF-8 bytes86.1
Whitespace-separated words13.0
BPE-style subwords (estimated at ~3.5 bytes/token, not measured)≈ 24.6
cql-ai ids (lexer tokens + roles)17.9

So lexer ids are 4.8× shorter than bytes and about 1.4× shorter than an estimated BPE sequence, not 10×. The bigger win is the vocabulary: 240 ids instead of roughly 50,000, which keeps the embedding table and the whole model tiny (576k parameters, 2.3 MB).

Model quality

On 10,000 statements from unseen synthetic schemas: macro-F1 0.977, exact label-set match 94.9%; four of six labels at F1 ≥ 0.99, the weakest, MissingPartitionKey, at 0.885. These measure fidelity to cqlc's analyzer on synthetic data, not accuracy on arbitrary real-world CQL.

Reproduce

# cqlc front-end, cql-ai latency and token stats
git clone https://github.com/Max-imalgutaussehend/cqlz && cd cqlz
cargo bench -p cqlz-benchmarks --bench frontend
cargo bench -p cqlz-benchmarks --bench inference
cargo run --release --bin token_stats

# cqlx (the db bench needs Docker)
git clone https://github.com/Max-imalgutaussehend/cqlx && cd cqlx
cargo bench -p cqlx --bench build
cargo bench -p cqlx --bench db

Not measured: cluster-scale throughput, tail latencies under load, comparisons of cqlc-generated code against the raw driver (it is thin wrappers over prepared statements, so we expect parity with the cqlx result, but have not run it).
