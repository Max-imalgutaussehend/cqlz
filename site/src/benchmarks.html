cqlz benchmarks: cqlc, cqlx, cql-ai and cqlz-gym measured --- Measured benchmarks for the cqlz family: cqlc vs sqlparser and KillrVideo coverage on Cassandra 5, cqlx on YCSB against the raw ScyllaDB driver and charybdis, cql-ai CQL HPC bottleneck detection, and cqlz-gym against an exact ILP. ---

Benchmarks

Real measurements, including the ones that do not flatter us. Every number is reproducible with the commands at the bottom.

Machine: Apple M3, 8 cores, 16 GB, macOS 27, Rust 1.99 release builds. ScyllaDB (latest image) runs in Docker on the same machine, so absolute numbers are indicative and ratios matter more. Criterion medians of 100 samples unless noted.

cql-ai

CQL HPC: predicting measured bottlenecks

5,284 statements were executed on ScyllaDB and on Apache Cassandra 5.0 over tables shaped like NoSQLBench, cassandra-stress, YCSB, TSBS and KillrVideo workloads, at several data sizes, 40 repetitions each. Labels come from latency ratios against a baseline point read (and against counterfactuals such as LIMIT 1 and a clean twin table), not from rules. The model sees the tokens of the statement and a 12-number description of your data.

Honest reading: the gain over keyword rules comes mostly from the data-shape numbers (rows per partition, tombstones, table size): without them the model reaches 0.62 to 0.68, barely above the rules. That is the point of a performance model, a statement is only slow relative to the data it runs on. Limits: one machine, single node in Docker, absolute microseconds are not portable, and no hot-key label because no signal was observable there. The released weights are trained on both engines pooled; the numbers above are from the ScyllaDB-only run so the Cassandra score is a true held-out engine test.

Cost of running it in CI

Statements are tokenised in 63 µs for a 36-statement file. The Transformer forward pass takes 41.7 ms for all 36 in one batch (1.1 ms for a single statement), against 108 µs for the complete cqlc analysis, so it is roughly 400 times slower than the compiler front end, and still far inside a CI budget. The two answer different questions: cqlc says whether a statement is valid and typed, cql-ai estimates whether it will be slow on your data.

On a real ScyllaDB

cqlz-gym validate loads the naive, greedy and best design into a real ScyllaDB (Docker, one node, 10,000 rows per entity, 32 clients, 6 s per design) and measures the workload mix. The three workloads are modelled on DataStax data-modelling examples (sensors, shopping) and KillrVideo.

WorkloadTables naive → bestModel-predicted costMeasured ops/sWeighted latency
sensors6 → 5−23 %+8.2 %726 → 671 µs

killrvideo7 → 70noise473 vs 486 µs
The direction of the model is right and its gain is overstated (−23 % predicted, −7.6 % latency measured). Run-to-run noise is a few percent on a laptop with Docker, so only the sensors result is clearly outside it. Where the best design equals the naive one (killrvideo), the differences between rows are noise.

One cqlc-core verification takes 3.1 µs, and the scaling efficiency is 96 % on two, 91 % on four and 67 % on eight threads (the last four cores of an M3 are efficiency cores). The environment is cheap enough that the search, not the checking, is the cost.

Reproduce

Run it yourself

# cqlc front end, cql-ai latency, token statistics, real-world KillrVideo check
git clone https://github.com/Max-imalgutaussehend/cqlz && cd cqlz/benchmarks
cargo bench --bench frontend
cargo bench --bench inference
cargo run --release --bin token_stats
cargo run --release --bin realworld

# cqlx vs raw driver vs charybdis (needs Docker)
cargo run --release --bin ycsb -- 50000 10

# cqlz-gym
git clone https://github.com/Max-imalgutaussehend/cqlz-lab && cd cqlz-lab
cargo run --release -p cqlz-gym -- eval --policy artifacts --instances 8 --exact-seconds 15

Not measured: cluster-scale throughput, tail latencies under overload, multi-node scaling, comparison with Cassandra rather than ScyllaDB.
