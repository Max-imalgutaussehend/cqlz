CQL-Gym

Question: can a small neural policy, trained by self-play against cqlc-core as an exact verifier, find good Cassandra table designs faster than integer programming, and keep working at workload sizes where the integer program stops being solvable?

Status: alpha proposal. Related work was found by web search (titles and abstracts, not read in full). We found RL for NoSQL index selection and for relational schemas, but none for Cassandra schema design; that rests on a handful of searches, not a literature review.

The idea

Data modelling in Cassandra means choosing denormalised tables so every query is a cheap single-partition read. The standard automated approach, NoSE (Mior, Salem, Aboulnaga, Liu, IEEE TKDE 2017), solves a binary integer program. Here a policy builds the design step by step, and the cqlc analyzer decides after each step whether a query is valid and warning-free against the proposed schema. Invalid actions are masked, so every design the policy proposes is valid by construction, and the reward needs no labelled data.

Why HPC

Self-play needs millions of environment steps, so the environment is the bottleneck. Our benchmark runs the complete cqlc analysis of 36 queries in about 103 µs (roughly 3 µs per query). That suggests 104 to 105 environment steps per second per core, an extrapolation we have to measure. The plan is a vectorised, allocation-free Rust environment scaled across cores, with learning on a GPU through wgpu, in the spirit of GPU-accelerated RL simulators.

What would make it wrong

Decided in advance: we drop or reframe the idea (none of these triggered in the first run) if the policy's median cost is more than 20 % above the ILP optimum where the ILP is solvable and it does not beat the greedy baseline at equal wall time where the ILP times out, or if environment throughput stays below 104 steps/s per core after optimisation.

Mean of cost divided by the best cost any method found on the same instance (1.000 = best). At 80–150 queries the exact solver gets 15 s and never finishes; the policy's argmax rollout takes 0.31 s on one CPU core. The environment runs at about 227,000 steps/s per core, and each cqlc-core verification call costs about 3.6 µs. Install: cargo install cqlz-gym or cqlz-markov (alpha, published on crates.io).

Caveats: the exact baseline is a simple branch-and-bound, not an integer-programming solver such as NoSE's, so a good ILP may close the gap. The cost model is synthetic and not calibrated on a cluster. Test workloads come from the same generator as training, so this shows generalisation to larger sizes only. Multi-core scaling was not measured.

Related work

NoSE (above) is the baseline and the source of the problem formulation. Neural combinatorial optimisation (Bello et al., 2016; Kool, van Hoof, Welling, ICLR 2019) trains attention policies with RL on combinatorial problems; the twist here is an exact, cheap constraint checker from a real compiler front end. Brax (Freeman et al., 2021) is the precedent for making the environment the scalable part. Closest existing RL work: index selection for NoSQL and relational schemas for multi-model data. Learned LSM cost models such as AXE (VLDB 2025) and CAMAL are candidates to replace the synthetic cost model.

Limits: the reward is a cost model, not a measurement, and a policy can exploit its errors, so final designs must be checked on a real ScyllaDB. Everything starts single-node on an Apple M3; scaling claims need a many-core machine.

CQL-Roofline

Question: can a typed CQL front end predict, before a query runs, an upper bound on its throughput and name the saturated resource (storage, network or CPU), as the Roofline model does for HPC kernels?

The Roofline model (Williams, Waterman, Patterson, CACM 2009) has recently been adapted to GPU query processing and to SSD-bound vector search. For wide-column stores the bytes per row can be derived statically from the cqlc IR. Falsification: drop it if the median attained/bound ratio is below 0.3 or the predicted bottleneck matches in fewer than 70 % of cases. It would later calibrate CQL-Gym's cost model. Full proposal.
