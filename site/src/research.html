Research α

An early proposal that connects the family to HPC. It is a plan with pre-registered failure criteria, not a result: nothing below has been implemented or measured.

Full proposal

CQL-Roofline

Question: can a typed CQL front end predict, before a query runs, an upper bound on its throughput and name the saturated resource (storage, network or CPU), as the Roofline model does for HPC kernels?

Status: alpha proposal. We could not verify novelty beyond our own searches; the first milestone is a proper literature review.

The idea

The Roofline model (Williams, Waterman, Patterson, CACM 2009) bounds attainable performance by min(peak compute, bandwidth × arithmetic intensity). It has recently been adapted to GPU query processing and to SSD-bound vector search; both need bytes per operation as input. For wide-column stores that number can be derived statically, because cqlc-core already resolves schema and query into a typed IR: column widths, key restrictions, ranges and limits.

rows/s  ≤  min(  BW_nvme / (a · w),          storage
               IOPS_nvme / (a · pages),      random reads
               BW_net / w_out,               network
               cores · f / c_row )           CPU

w = bytes per row from the types   a = read amplification (measured)
the minimizing term is the predicted bottleneck

What would make it wrong

Decided in advance: we drop or reframe the idea if the median attained/bound ratio is below 0.3, if the predicted bottleneck matches the measured one in fewer than 70 % of cases, or if the model needs so much per-table fitting that it stops predicting.

A Rust shard-aware loader and scanner (token hashing in batches, per-shard batching) keeps the client from being the bottleneck. ScyllaDB's own petabyte benchmark reports that a shard-aware driver is essential at scale; we found no independent HPC-style ingest study.

Related work

NoSE (Mior, Salem, Aboulnaga, Liu; IEEE TKDE 2017) selects Cassandra schemas with an integer-programming cost model. CQL-Roofline does not design schemas; it bounds given ones, and could later supply such optimizers with a hardware-grounded cost term.

Limits: alpha runs on a single Apple M3 with a ScyllaDB container and can only support single-node statements. Scaling claims need a real cluster (Slurm or cloud nodes).
